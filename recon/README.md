Reconstructed source for `Bugs.exe`, PC v1.0.

Everything in this directory except this file is generated by
[`tools/recon.py`](../tools/recon.py) from `Decomp/bugs_pseudocode.c` -- the raw
Hex-Rays export of the game -- combined with what the repository already knows
about the game in `doc/src/funcs.csv`. Regenerate with:

```
python3 tools/recon.py
python3 tools/check_recon.py
```

`COVERAGE.md` records what the current run produced.

The export is v1.0: all 159 of the `PC v1.0 addr` entries in `doc/src/funcs.csv`
land on a function in it, and none of the v1.6 ones do. Note that
`Decomp/bugs.exe`, which the string addresses are recovered from, hashes to
`4D0E725A110162E2A454BBF7AAB8FAFD` rather than the v1.0 MD5 given in the
top-level README, so it is not the same file byte for byte even though it shares
v1.0's layout.

# What This Is (And Is Not)

This is the export reorganized into something that reads like source: functions
carry their real names, calls resolve to those names, data references resolve to
named addresses, and the whole thing is split into files that approximate the
game's original translation units.

It is **not** a decompilation. Nothing here has been read, understood, or
rewritten by hand -- that is what [`BugsDecomp/`](../BugsDecomp) is for, and the
code there is the authority wherever the two overlap. The intent is to give that
work a better starting point than a 72,000-line export, and to make the parts of
the game nobody has looked at yet browsable.

For the same reason it does not compile, and is not wired into the solution.
Hex-Rays emits constructs with no C spelling (`__usercall` and its register
assignments, jumps into the middle of another function) and infers types that
are only sometimes right. `defs.h` supplies what it can and marks its
approximations.

# Layout

- `defs.h` - the types and helpers Hex-Rays output relies on
- `gamedata.h` - every data symbol the code refers to, as an address macro
- `gamefuncs.h` - a declaration for every reconstructed function
- `bugs.h` - umbrella header, included by each module
- `COVERAGE.md` - generated statistics and the module table
- `*.c` - the modules

Data symbols are macros naming a fixed address, the same way the hand-written
code in `BugsDecomp/` refers to game memory:

```c
#define dword_45C338       (*(int *)0x45C338)
#define aRt                ((char *)0x467700) // "rt"
```

# How Much To Trust It

Different parts rest on different evidence. In descending order:

**Function addresses and bodies.** Straight from the export; the only changes
are the rewrites listed below, and `tools/check_recon.py` verifies that they
moved nothing else.

**Function names.** Taken from `doc/src/funcs.csv` by address, so they are
exactly as good as that file. 159 of the export's 968 functions have one; the
rest keep the `sub_<address>` name IDA gave them. Where several documented
functions share one address -- identical code the linker folded together -- the
first name is used and the others are listed in the comment above the function.

**Data symbol addresses.** Encoded in the IDA symbol name itself
(`dword_45C338` is the dword at `0x45C338`), so they are certain. Their *types*
are only as good as the prefix IDA chose.

**String literal addresses.** Recovered from `bugs.exe`, because IDA does not
put a string's address in its symbol name. Each candidate string in the image is
run through the naming rules IDA uses, and a symbol is accepted only when the
number of candidates matches the number of symbols sharing that base name
exactly -- IDA suffixes collisions `_0`, `_1`, ... in address order, so the counts
pin the mapping down. 101 of 107 resolved this way; the rest are declared
`extern` with their candidates listed, to be settled by hand.

**Module boundaries.** Inferred, and the weakest link here. The compiler emits a
translation unit's functions contiguously, so a run of undocumented functions
sitting between two documented ones of the same subgroup is taken to belong with
them. Files named `unk_<address>` are runs that could not be attributed to
anything; they are named for where they start and are very likely several source
files each, not one.

Two modules are named from harder evidence: the game leaves its own source file
names in assert-style strings, so the functions quoting
`D:\Projets\Bugs\src\Pcrogl.c` and `D:\Projets\Bugs\src\pcrsoft8.c` are known to
come from those files. `rogl.c` is the former -- the same file the repository
already calls `rogl` -- extended over the documented `port/rogl` functions that
sit between its two ends. `winmain.c` is the run containing the game's `WinMain`.

The MSVC runtime is gathered into `crt.c` regardless of address. It is
interleaved with the game's own object files, and letting it split the runs
would fragment game modules along boundaries that say nothing about the game's
source layout.

# Rewrites Applied

Hex-Rays output is not quite C. The following are normalized, and nothing else
is touched:

| from | to |
|------|----|
| `f(Buffer: p, MaxCount: 80)` | `f(/*Buffer*/ p, /*MaxCount*/ 80)` |
| `f(a1: x, a2: y)` | `f(x, y)` |
| `sub_401000` | `InitTrack` (and every other documented name) |
| `nullptr` | `NULL` |
| `MEMORY[0x46774C]` | `(*(int *)0x46774C)` |
| `f@<eax>(int a1@<ecx>)` | `f/*@<eax>*/(int a1/*@<ecx>*/)` |
| `__spoils<edx,ecx> f()` | `/*__spoils<edx,ecx>*/ f()` |

The placeholder parameter names Hex-Rays invents (`a1`, `a2`, ...) carry no
information and are dropped; the ones it took from a real prototype are kept as
comments.

# Working From This

To decompile a function properly, find it here, then write the real version in
`BugsDecomp/` following the conventions in the [top-level README](../README.md):
name it, give its arguments types and meaning, refer to game memory and game
runtime functions rather than to fresh copies, and register the patch with
`PATCH_CODE`. Then add it to `doc/src/funcs.csv` and regenerate -- the next run
will name it here, and at every call site across the other modules.
